# LogLens

**Search 50 GB of logs with a 22 kB binary.**

```
$ ls -l bin/loglens
-rwxr-xr-x 1 user user 22786 loglens

$ ./bin/loglens -s 500 /var/log/huge.log
633807
```

Forty seconds for fifty gigabytes, on a laptop with sixteen. No index, no database, no
runtime, and nothing to install — the binary is statically linked and has no shared
libraries at all.

It keeps up with the same program written in Go, which is ninety times its size — and the
compiler that produced it has no optimisation pass and took three milliseconds.

## What it does

```bash
loglens <pattern> <file>        every line containing the pattern
loglens -c <pattern> <file>     count them instead of printing them
loglens -s <status> <file>      lines with that HTTP status, counted
```

`-s` is not a substring search: `500` also appears as a response size and inside an
address, so it looks for the status where a status actually sits — between the closing
quote of the request and a space.

## How, in thirty lines

The file is **mapped, not read**. The kernel pages in what the scan touches and reclaims
it again, so the program holds 24 kB of its own memory whether the file is one megabyte
or fifty gigabytes. There is no buffer to size, no streaming loop to get wrong, and no
allocation anywhere in the program.

```pascal
base := sys6(SYS.mmap, 0, size, PROT_READ, MAP_SHARED, fd, 0);
...
search(view(base, size));          // the whole file, as an array of char
```

That is the entire mechanism: `mmap` gives an address, `view` turns an address and a
length into an ordinary array, and from there the file is just bytes you can index. The
search loop uses `scan`, a builtin that finds one byte, and only compares the rest of the
pattern where the first byte hits.

## The measurements

One laptop, six cores, 16 GB of RAM, 15 September 2026. Every log generated by
`tools/genlog.wz` with the default seed, so you can repeat all of it.

| size | generate | search | rate | matches (status 500) |
|---|---|---|---|---|
| 1 MB | 5 ms | 2 ms | 500 MB/s | 9 |
| 10 MB | 44 ms | 6 ms | 1.7 GB/s | 117 |
| 100 MB | 445 ms | 38 ms | 2.6 GB/s | 1,207 |
| 1 GB | 4.6 s | 394 ms | 2.6 GB/s | 12,714 |
| 10 GB | 45 s | 3.7 s | 2.8 GB/s | 126,494 |
| **50 GB** | **3 m 10 s** | **40 s** | **1.3 GB/s** | **633,807** |

**The 50 GB file is 3.4× larger than the machine's entire RAM**, which is the number that
matters: at that point the rate is what the disk can deliver, not what the program can
process. Below that, once the file fits in the page cache, it holds at about 2.7 GB/s.

### Against everything else on the machine

Same job, same 2 GB file, page cache warmed first so this measures the programs and not
the disk. **Every one of them answers 25492** — which is what makes the comparison worth
anything.

| | time | peak RSS | binary |
|---|---|---|---|
| **`loglens -s 500`** | **0.72 s** | 2,097,152 kB | **22,786 B** |
| Go, mmap + `bytes.Index` | 0.82 s | 2,098,816 kB | 2,040,611 B |
| Go, `read()` in blocks | 1.17 s | 24,452 kB | 2,040,611 B |
| `ugrep -c` | 1.33 s | 2,304 kB | 186,824 B |
| Python, `count()` per block | 2.43 s | 27,000 kB | interpreter |
| `awk` | 3.26 s | 3,840 kB | interpreter |
| Python, per line | 4.79 s | 40,040 kB | interpreter |
| `bash` read loop | ~29 s (extrapolated) | — | interpreter |

The `grep` on this machine is **ugrep 7.8.4**, not GNU grep — worth saying, because the
two are different programs with different performance.

### What this actually shows, and what it does not

**The speed is mostly `mmap`, not clever code generation.** Compare the two Go rows: same
language, same pattern, same answer, and the only difference is mapping the file versus
reading it in blocks. That is where most of the gap comes from. The 14% that remains
between us and Go-with-mmap is not explained yet, so it is not claimed.

**What is worth claiming is what it cost to get there.**

| | to build this program | binary |
|---|---|---|
| **Wantzel** | **3 ms**, no optimisation stage at all | **22,786 B** |
| Go | 2,651 ms cold, 112 ms warm — SSA, register allocation, inlining | 2,040,611 B |

The usual trade is: fast builds or fast output, pick one. A debug build compiles quickly
and runs slowly; a release build the other way round. **For this kind of work that trade
did not appear.** This compiler has no optimisation pass — the same compiler translates its
own 6,772 lines in about ten milliseconds — and the result keeps up with a fully optimised
Go binary ninety times its size.

That will not hold everywhere. This is a tight loop over bytes with a SIMD scan underneath,
which is exactly where an optimiser has least to find; code leaning on deep abstraction or
many small functions is where inlining earns its keep. The claim is for this kind of work,
not in general.

**Size is the measure with nothing to argue about:** 22,786 bytes against 2,040,611, both
statically linked, no shared libraries, no runtime, no dependencies.

### The memory column is the honest half

LogLens maps the whole file, and the kernel counts every page it has paged in as resident —
even though it can drop them at any moment and does. Measured with `smaps_rollup` during a
2 GB scan:

```
Private_Dirty:        24 kB     <- what the program actually owns
Private_Clean:    438484 kB     <- file pages, reclaimable, not really "used"
```

**And that is not a Wantzel property.** Go-with-mmap shows the same 2 GB resident; anything
that maps a file does. Streaming (`ugrep`, `awk`, Go-with-`read()`) never holds more than a
few megabytes, and that is a real advantage if you need a hard ceiling. So neither column is
a lie and neither tells the whole story: if you need bounded resident memory, stream. If you
want the shortest program that walks a file at disk speed, map it.

## Reproducing all of it

```bash
./wzlrun --build                   # two binaries, about a second
./wzlrun --ladder /tmp/logs        # 1 MB up to 10 GB, cleaning up as it goes
./wzlrun --ladder /tmp/logs 50     # including the 50 GB rung (needs ~54 GB free)
```

**The generated logs never go into this repository**, and `wzlrun` refuses a directory
inside it. Fifty gigabytes in git cannot be taken out again: what is once in the history
stays there.

## The generator is half the demo

`tools/genlog.wz` writes nginx-style access logs, and it is written in Wantzel like
everything else here. Generated rather than downloaded for three reasons: anyone can
reproduce the measurement without a multi-gigabyte download, there is no licence or
privacy question, and writing tens of gigabytes with a 20 kB binary shows the same
property as searching them.

**The shape is the point.** A generator that gives every line the same length and spreads
status codes evenly would make searching artificially easy — you would be measuring
nothing. So:

- **status codes in real proportions** — 93% `200`, 3% `404`, and `500` at 0.17%, which
  makes "find every 500" a genuine needle rather than a third of the file
- **a long tail of endpoints** — a few paths carry most of the traffic, twenty-odd are rare
- **request times that peak during the day**, so an hour's worth varies by which hour
- **response sizes and durations two orders of magnitude apart**

It carries its own seeded PRNG rather than using `lib/rand.wz`, which reads the kernel's
entropy and deliberately has no seed. The same seed gives the same bytes on every
machine, which is what makes the table above checkable rather than quotable.
